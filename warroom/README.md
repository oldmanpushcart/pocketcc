# warroom —— 战报下载 / 解析 / 分析系统

> pocketcc 仓库的并列子工程之一。回链：[根 README](../README.md) · 兄弟工程 [extension](../extension/README.md)、[dashcam](../dashcam/README.md)

`warroom` 读取《口袋奇兵》的战斗结算记录（战报 / report），把重字典 ID 编码的原始 JSON
解析为结构化数据并持久化，后续叠加规则统计与大模型分析，产出**整体 + 攻方 + 守方**三份
改进建议。同时沉淀玩家档案，供跨战报统计战力情况。

## 定位与命名

命名延续 [dashcam](../dashcam/README.md)（报文"行车记录仪"）的英文隐喻风格：dashcam 管"录"，
warroom（作战室）管"复盘推演 + 给决策"。本工程**独立于**扩展与 dashcam，自带 `package.json`，
不参与根 `esbuild` 构建，仅按需读取游戏侧产出的战报数据。

## 数据链路

战报正文存于阿里云 OSS，**链接限时有效会过期**，因此第一要务是"抓到即永久缓存原文"。

```
战报ID  ──link.js──►  OSS URL  ──fetch.js──►  raw/{prefix4}/{id}.json (永久留档)
 (4878890640079697925)         │                        │
                               └── 读信封字段 ──────────►  SQLite reports 索引
```

URL 拼写规则（已实测，无需登录态）：

```
{baseUrl}/prod/{id前4位}/{完整ID}.json
4878890640079697925 → https://fight-report.oss-accelerate.aliyuncs.com/prod/4878/4878890640079697925.json
```

## 安装

```bash
cd warroom
npm install          # 唯一三方依赖：better-sqlite3（含原生二进制）
```

要求 Node.js >= 18（使用全局 `fetch`、`AbortSignal.timeout`）。

## 配置

复制 `config.example.json` 为 `config.json`（后者已 gitignore，可安全填写私密值）：

```bash
Copy-Item config.example.json config.json   # PowerShell
```

- **AK 走环境变量**：`config.json` 里 `"apiKey": "${WARROOM_LLM_AK}"` 会被自动展开为同名环境变量值；
  环境变量缺失时该字段解析为 `null` 并记录，**不会**把占位符原文写库，也不阻断 `fetch`/`info`。
- 路径均可用 `WARROOM_DATA` 覆盖数据根目录；`WARROOM_DEBUG=1` 打开 debug 级日志。
- **`storage` 里只有 `dataDir` 生效**：`dbPath` / `rawDir` / `dictDir` 三键由 `src/config.js` 用 `dataDir` 派生覆盖（`warroom.db` / `raw` / `dicts`），写在配置里只是给读者看的形态说明，改它们不影响落点。

## 使用

```bash
node cli.js fetch <reportId...> [--force]   # 下载（默认幂等：本地已有则跳过网络）
node cli.js import <file.json> <reportId>   # 导入已在本地的原始战报文件
node cli.js dict [--force]                  # 获取/刷新游戏侧字典快照
node cli.js parse [<reportId...>]           # 原文 → 结构化入库（含 blob 富化；不给 id = 处全部）
node cli.js html  [<reportId...>]           # 渲染战报工作台 HTML → analysis/<id>.html（不给 id = 处已解析全部）
node cli.js info                             # 查看库/落盘状态与迁移版本
```

示例（本仓库已实测跑通）：

```bash
node cli.js fetch 4878890640079697925 4878890262508451849
node cli.js info
```

## 存储设计

**双层持久化**（详见 [`src/schema.js`](./src/schema.js)）：

| 层     | 存什么                                 | 位置                       |
| ------ | -------------------------------------- | -------------------------- |
| 文件层 | 下载的原始战报 JSON、字典快照          | `data/raw/`、`data/dicts/` |
| SQLite | 解析后的结构化数据、玩家档案、分析结果 | `data/warroom.db`          |

三条建模原则：

1. **冷热分离**：高频统计字段（战力、结果、uid、时间）摊平成列；`formation_v2`、`enigmas`
   等待考证容器先存 JSON 列，解码一个、拆列一个，解析进度不堵建模。
2. **64 位 ID 一律 TEXT**：`report_id`/`uuid`/`march_id`/`uid` 超 `2^53`，绝不 `Number` 化，杜绝精度丢失。
3. **字典版本随行**：`reports.dict_version` + `dict_entries` 带版本键，历史战报可按当时代码复现。

表清单（`PRAGMA user_version` 当前为 **4**，`MIGRATIONS` 逐版累加）：`reports` · `battle_marches` · `sides` ·
`side_players` · `side_units` · `unit_instances` · `battle_events` · `players` · `dict_entries` ·
`rule_findings` · `analyses`，另加两张归一表 —— **`buff_effects`**（v2：把散落在各编配视图的数值加成统一成一行一
buff，每行带 `source_view` 供分源聚合且不重复计数）与 **`damage_sources`**（v3：伤害归因行）。
`battle_events` 在 v4 从「只有 `raw` JSON」升级为带语义列（`kind` / `outcome` / `act_type` / `e_type` /
`e_value` / `old_hit` / `trigger_type` / `ev_id` / `targets` / `nums` / `buff_src` 由 parse 直算，
`buff_name` / `buff_type` / `buff_is_minus` / `buff_target` / `buff_value_type` / `buff_sustained` /
`buff_debuff_time` / `skill_name` / `hero_name` 由字典回填），并建 `kind` / `buff_id` 两个索引——
历史库需重跑 `node cli.js parse` 才有这些列。
其中 `analyses.scope` 取 `overall/attacker/defender`，正好对应三份报告。

信息架构：一级导航有**三个 TAB** —— 「基本信息」（`mv-info`）、「伤害汇总」（`mv-home`）与「回合伤害」（`mv-round`）；
原「战斗」TAB 已折进基本信息 TAB；除静态编配（英雄/机甲/军阵基础配置已提为常显卡片）外，其余逐件明细仍落在 `fold` 内、不提供隐藏入口。所有内容服从一条主轴动线：
**这一战是谁打谁 → 双方伤害分别由什么构成 → 哪些增益／属性造成了这个差 → 差是在哪一回合拉开的**。
伤害汇总 TAB 依次为战果简介 → 伤害构成（主轴本体）；基本信息 TAB 为阵型位置 → 静态编配（英雄/机甲/军阵基础配置常显）→ 增益对比（首卡按属性大类累加）→ 属性模块构成；回合伤害 TAB 为「总览 + 逐回合五段」。

主轴四纪律（每个板块都必须遵守，不再自创组织话术）：

1. **一律攻守并排**：所有对比统一用蝴蝶行 `divergingRows`（攻左红 / 守右蓝 / 共用标尺 / 尾随 Δ），
   禁止两侧各自归一的并排柱。
2. **一律可对账**：每个板块首行给「合计」，且合计回到同一分母——伤害类回 `acc.dmg`（总输出）、
   逐回合回 `roundAgg.dealt`、逐槽承伤回四类伤害事件 `val` 合计、属性模块回本场 `buff_effects` 行数；
   板块末尾用一行 `.note` 写明对账口径。
3. **一律「汇总常显 + 明细默认折叠」**：主视图只到「组」级（来源类别 / 军种 / 增益属性 / 模块组），
   逐件、逐技能、逐槽一律走 `fold()` 默认收起。
4. **主轴关联不臆造**：增益／属性板块只给「属性差值榜 + 与伤害类别差值榜并列」，不用静态编配猜因果
   （静态 `buff_effects` 无回合列、无伤害归属）。

其余基础纪律：

- **阵营色**：攻方一律 `--att`（红）、守方一律 `--def`（蓝），模块内「攻方/守方」小标题走
  `.side-tag`，禁止内联 `style="color:..."`。军种三色（陆/海/空）与专精金黄是**另外的语义**，不与阵营色混用。
- **TAB 命名**：一级 `mv-info|mv-home|mv-round`、回合二级 `rd-*`（总览 + 第 1..N 回合，`N` 取实测最大回合序号、
  数字 key 直接可用）、英雄三级 `hy-*`、军阵三级 `fm-*`；一律由 `tabs()` 产出，不手写「按位置枚举」的规则。
- **口径诚实**：战报没下发的字段不臆造。两批「看着该有、但战报给不出」的断言（战斗维三处 +
  回合／时长维三条）已按复核后的事实改写过，结论与证据数见
  [可得性复核](#三处可得性断言的复核不是同类假阴性才敢写死) 与
  [回合与时长维的二次复核](#回合与时长维的二次复核又抓到两条错判据)。

### 属性模块分组口径（基本信息 TAB · 属性模块构成）

最详细一层按**来源模块**拆分属性，分组表 `ATTR_MODULES`（`data.js`）**按 `source_view` 精确枚举**，
未被列中的 view 一律落入 catch-all 的「其他编配系统」组（`MOD_OTHER`，旧名「其他来源」，实际包含
联盟/VIP/材料/图鉴/秘密武器/城市技能/世界奇观/type:94/96 一类未归入 11 大独立模块组的游戏系统 buff，
不是「查不到来源」），禁止静默丢行：

| 模块组   | 归入的 `source_view`                                                                                                      | 逐件明细（`parts.js` `modDetail`）     |
| -------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| 机甲     | `mecha_chip` `mecha_skill` `trace:MECHA`                                                                                  | 属性行（富面板→静态编配常显）          |
| 兵种装备 | `trace:ARMY_EQUIP` `trace:INIT_ARMY_EQUIP`（排除克制名 `notRe`）                                                          | 新旧装备 chip 列表                     |
| 装备强化 | `army_mastery` `trace:ENHANCE_MASTERY`                                                                                    | 兵种强化                               |
| 兵种克制 | `trace:CAREER` 中 `KEZHI` 命中项                                                                                          | 天赋                                   |
| 元素伤害 | `trace:ELEMENT`                                                                                                           | —（`elementCard` 直出 elemPairs）      |
| 英雄     | `hero_equip` `hero_equip_stone` `hero_talent` `trace:HERO_EQUIP` `trace:HERO_BOND` `trace:HERO_TALENT` `trace:HERO_SKILL` | 属性行（`hy` 三级富面板→静态编配常显） |
| 军阵     | `formation_*` `trace:FORMATION_V2*` `trace:THOR_SCIENCE` `trace:SCIENCE`                                                  | 属性行（`fm` 三级富面板→静态编配常显） |
| 装饰     | `decoration_suit` `decoration_sublime` `decoration_exp` `trace:DECORATION`                                                | 套装 / 升华 / 拥有件                   |
| 皮肤     | `skin_*` `trace:SKIN` `trace:MARCH_SKIN` `trace:CASTLE_EFFECT` `trace:CITY_SKIN`                                          | 皮肤 / 展览 / 城堡                     |
| 异能兽   | `enigma_beast` `enigma_field` `trace:ENIGMA_BEAST` `trace:ENIGMA_FIELD`                                                   | 异能兽 / 领域                          |
| 跨服收藏 | `cross_collection` `trace:CROSS_TREASURE_COLLECTION`                                                                      | 收藏行                                 |
| 其他编配系统 | 上表未命中的全部 view（`trace:ALLIANCE*` `trace:MATERIAL` `trace:VIP` `trace:STAMP` `type:94/96` 等）                              | 按本组 view 域化 `buffAttrDetail`，`SRC_ZH` 解名 |

覆盖不变量（渲染时校验、写进属性模块构成末尾 note）：**Σ 各模块组命中行 == 本场 `buff_effects` 全部行**，
命中不上的落「其他编配系统」。卡片标题行 `rowCnt` 计本组 views 下全部 buff_effects 行（含无名行与非属性 buff），
而 pairs 只 sum 有中文名且匹配 `BUFF_ATTR_RE` 的属性行，两者数量不等属数据特性、非渲染 bug。增益对比是「全场聚合视图」（跨全部 view 按属性名累加）、属性模块构成是「分源视图」
（只本组 view），两者同走 `cmpAgg` 原语、口径互补、不重复计数。属性为开局静态编配量（`buff_effects`
无回合维度），故逐回合只给增益活动、不给属性对比。

> **按属性大类累加**（`data.attrCatAgg`，增益对比首卡）：把跨全部来源的增益再粗一级归到「生命 / 攻击 / 防御 / 伤害
> 加深 / 伤害减免 / 兵种克制」六类求和，走 `divergingRows` 攻守并排；同一类若既有万分比又有绝对值则按 `value_type`
> 拆两行（量纲不同不相加）。比按属性名的 `cmpAgg` 更粗、比按来源模块的 `attrModules` 更抽象，三者互不可替代。

### 逐回合兵力：战力衰减走势 + 九宫格逐格残力

回放里能逐格逐回合看到消耗，靠的是**伤害事件 `power` 列在被击方（`target`）上＝该次结算后的剩余战力快照**。
实测（4883545741242523653）：同一槽位取到的 `power` 沿结算序（`idx`）单调不增、槽首值≈`side_units.max_power`、
终值≈终局残力（全库 41/45 场下发，4 场为早期结算阶段场次不带此列）。据此给两个视图：

- **总览·战力衰减走势**：逐回合末，双方剩余战力按「开局双方 `max_power` 之和」同尺归一的并排柱
  （两根柱之和随歼敌递减，可读作此消彼长）。
- **回合卡·九宫格残力**：复用首页 `gridHtml` 版面，`extra` 在每格追加该槽位「本回合末剩余 / 开局 · 占比」条；
  未被击的格显式标「无新快照」而非补 0。

**残留的粒度边界**（不是做不出、是只到这个精度）：`IndexRound` 标记落在**回合末尾**（实测 idx 2 / 1007 / 1966 / 2487），
回合起点无独立快照，故「本回合未被击」与「被击但未掉战力」不可区分——前者沿用上一回合末值（`atRound` 取 ≤该回合的
最近快照，首快照之前的回合按 `max_power` 计），图上不另作标记。战力可被增援/补给抬高，故**只当剩余快照、不当累计承伤**
（累计承伤一律看伤害构成节）；`seq` 9/10 增援溢出格不在九宫格、只进侧级合计与走势柱。

### 回合维的两条永久数据边界

以下两件「看着该有、但战报给不出」的事已经实测判死，写进了回合模块产物末尾的「本模块的数据边界」卡，
**不要再当成待实现重开**（旧版本此处曾列三件，其中「逐回合血条分布」已由上面的 `power` 快照翻案落地；

### 台账拆三本的分侧判据：为什么只能按携带者

三次复核后的台账是单表 8 列（归属 / 获得 / 挂在谁身上 / 从谁身上摘），用户反馈仍**分不清“这是谁的增益”**。
拆之前先量化两种拆法能覆盖多少（临时探针跑完即删，样本 = 45 场全库 **1,566 个 `(场, buff_id)` 组**）：

| 分侧依据                                                                     | 攻  | 守  | 双方互挂 | 无处可放        |
| ---------------------------------------------------------------------------- | --- | --- | -------- | --------------- |
| **携带者**（挂在谁身上：`target` 点名，没点名退到 `RemoveSkillBuff.source`） | 557 | 599 | 286      | **124（7.9%）** |
| 施加者（谁挂的：施加事件 `source`）                                          | 295 | 280 | 192      | **799（51%）**  |

- **按施加者拆会塌一半**：一半 `buff_id` 在某场里只被摘除过、没有在先的施加行（即台账里那类“仅摘除”行）。
- **未点名那 124 组消不掉**：45 场里 **0 场**做到“零未定侧”，因为占施加类多数的 `ADDMUTIBUFFS` 一条都不点名携带者——
  这是下发边界，不是实现遗漏，故单独立一本而不是归到任意一侧。
- **事件级不丢**：21,100 条移除按携带侧分是攻 8,079 / 守 6,098 / 双方共用 `buff_id` 6,923，**0 条落空**；
  丢的只是“把整个 `buff_id` 归到一侧”的判定。
- **落地形态**（按上表选定的四条）：① 两本主台账并排、各自 6 列（分侧由本标题承载后，“归属”与“挂在谁身上”两列变冗余，8→6）；
  ② 互挂项**两本各列一份**，页脚用「攻本 + 守本 − 互挂 = 可分侧」校正行数；③ 未点名单开第三本、只 4 列且不进实测时长；
  ④ 旧的**合并总账不保留**（三个真相源就是上次 `source` 语义翻车的温床），“看全”由两本页脚的全场合计承担。
- **归类阈值**：携带侧取多数侧；两侧都有量且少数侧 ≥ 多数侧 25% 则记「双方互挂」（否则 4/4、5/4 会被抛硬币归一边）。
- 页脚举例只从**本台账内真实存在的单侧行**取数字，不拿另一本的数值来套（否则守本会读出“守方往守方身上灌”）。

  `npx eslint --no-ignore --max-warnings=0 warroom/src/html.js warroom/src/html`。
- 改动渲染层后必跑全量 `node cli.js html`，并对账「伤害构成四维合计 == KPI 总输出」「逐回合本回合造成合计 == 总输出」
  「拍轴『造成』行回合合计 == 该回合本回合造成」（三者同源于 `battle_events.val`，拍轴与回合卡是同一判据的两种切法）。
  逐槽承伤另有一条自己的对账：「各槽承伤合计 + 归不上槽的金额 == 四类伤害事件 `val` 合计」（实测 45/45 场成立、
  归不上槽的为 0）；「本侧承伤 == 对侧造成」在 44/45 场成立，例外那场（4885059974979510277）的差额来自 9 条 `source` 解不到侧的伤害事件。
  两 TAB 重排后另有两条对账（同源于 `buff_effects` / 施加事件）：属性模块分组的「Σ 各模块组命中行 == 本场 `buff_effects`
  总行」（覆盖不变量，`modAgg` 内置未命中入「其他编配系统」兜底）；逐回合增益「`roundAgg.applyAttr` 各回合属性合计 ≤ 该回合施加总数」。
  逐回合兵力另有一条（`forceAgg` 构造保证）：「走势柱某侧某回合末剩余 == 该侧九宫格九槽 `atRound`（≤该回合最近快照、否则 `max_power`）之和」；
  `power` 列在被击方的同一槽位应沿 `idx` 单调不增（实测 41/45 场成立，4 场早期结算阶段场次不带此列、走势卡显式回落）。
- 探针脚本放 `warroom/scripts/`，**结论进了本文档的才留档**（现有 26 个：`dict-*` / `*-probe` / `*-scan` 是各次取证的可复现入口，
  换字典版本或新语料时要靠它们重跑，不许删）；一次性试跑、结论没进台账的用完即删，别把仓库当草稿纸。
- 忽略项：`node_modules/`、`data/`（原文 + 字典 + SQLite）、`config.json`（含本机路径与密钥引用）、`analysis/`
  （HTML 渲染产物，可由 `node cli.js html` 再生）、`*.part`（原子落盘中间态）。
