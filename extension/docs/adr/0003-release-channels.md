# 发布通道是版本号之外的独立维度（dev / snapshot / release）

需要三档构建：开发档在作者机器上调试（不该被 OSS 上任意一次发布打断）、快照档作者自己先吃真实分发链路、正式档发给朋友。最初的提法是把档位写进版本号（`1.0.0-dev` / `1.0.0-snapshot`），并给开发档与快照档加存储前缀。定稿改为：**通道是版本号之外的独立维度**（构建期注入 `__PCC_CHANNEL__`，取值 `dev|snapshot|release`），一个版本号可以按任一通道出包，转正就是把同一批代码换个通道重发一次。

## 为什么通道绝不能进版本号

升级判定 `cmpVer()` 按点分段 `parseInt(x, 10) || 0` 比较，`parseInt('0-dev')` 恰好得 0 —— 于是 `cmpVer('1.0.0-dev', '1.0.0') === 0`。「dev 比正式版旧」这个直觉是反的，实际后果是**静默不更新**：客户端认定已是最新，一声不吭。此外 `manifest.version` 只接受 1–4 段纯数字，`publish-oss.mjs` 的形态校验 `/^\d+(\.\d+)*$/` 同样会拒掉带后缀的号。三处约束同向，没有回旋余地。

## 为什么是三组 key、三个扩展 ID

只加存储前缀不足以让三档并存：`chrome.storage.local` 的隔离边界是**扩展 ID**，而 ID 由 `manifest.key` 派生。带着同一个 key 的三个目录在 Chrome 眼里是同一个扩展，第二个直接 ID 冲突、装不上。所以三档各持一组 key（`extension/channel-keys.json`，只含公钥派生物、不含私钥），换来三个互不相干的实例：数据天然隔离、可同时安装。tracked 的 `extension/manifest.json` 存的是 **dev key**，正式与快照的 key 在打包时按通道注入——这条安排是为了让正式 ID 从此不再变动（朋友手上的实例与数据不受后续任何改造影响）。

实例命名口径一律带通道后缀（`.dev` / `.snapshot`，**正式刻意留空**）：postMessage 协议名 `NS`、存储键前缀根段 `STORAGE_ROOT`、升级三键 `pccupd*:bundle|state|pref`。收口在 `core/constants.js` 一处，漏一处就留下一条跨通道互踩的通路——三档都往同一个游戏页的 MAIN world 注入，两套远程体并存等于同一个账号跑了两套自动化。留空后缀的代价换来了存量用户零迁移。

## 补充：快照通道的发布身份带正文摘要

通道成为独立维度后，「一号一正文」在快照通道上变成了累赘：作者一天吃五六轮构建，每轮都被迫 `Z++`（否则 `cmpVer` 相等即 `stay`，手上那台机器拉不到新正文），正式版还没发出去，号已经被快照吃到了 `1.0.9`。定稿：**快照通道的发布身份是 `版本号@正文 sha256 前 8 位`（`1.0.0@03b39054`），正式通道只用版本号**——朋友侧的「一号一正文」是一句存量保证，不动。

三个支撑点：

- 摘要与版本号正交，所以不会重踩本节开头那条红线：它**不进 `ver` 字段**，只在客户端拼身份串（`core/update.js` 的 `identityOf` / `pendingIdentity`）。把 `@03b39054` 拼进版本号会被 `cmpVer` 逐段 `parseInt` 折叠成 `0`，等于换个写法重演一遍「静默不更新」。
- 正文对象名同步带上摘要段（`pocketcc-remote-1.0.0-03b39054.js`）：同号重发落在**不同对象**上，`Cache-Control: …, immutable` 没有被违背，旧正文也不必删（删了会让已拿到它的机器回滚不了）。清单里的 `file` 就是这个名字，所以清单索引要优先按 `file` 取标签（`tagsFor`），否则同号的两份条目会拿错摘要。
- 人工位（「稍后」/ 执行崩溃隔离）按身份而不是按号记账：快照通道里只消掉 `1.0.0@aa11bb22` 那一份，同号的另一份正文照旧会提示。旧键 `dismissedVer` / `blockedVer` 仍可读出，写入走 `dismissedId` / `blockedId`，存量配置不抹。

分叉只由 `CHANNEL_NAME !== 'release'` 得出（`DIGEST_IDENTITY`）：正式构建与未注入通道的测试同态，身份串退化成纯版本号，release 侧的判据与既有断言一字不变。`tests/core/channel-isolation.test.js` 把这条分叉也守成源码级纪律：不许有人绕开通道常量自己比字面量。

## Considered Options

- **版本号后缀 `1.0.0-dev`**：被 `cmpVer` 判成同版本，见上。
- **快照走版本号第四段**（`1.0.0.1`）：能过校验也能正确排序，但在通道已成一等维度后属多余约束，且会让"同一个号能不能双通道发出去"重新变得含糊。曾写入 README，现已撤销。
- **只加存储前缀、共用一个 key**：装不上第二个实例，前缀也就无从隔离。
- **给正式实例也加后缀**：一次性抹掉所有存量数据与朋友配置。
- **快照每轮都 `Z++`**：能用，但号会被先吃光，转正时看起来像已经发过好几轮，也拿不到「转正不必升号」的好处。
- **三档统一用摘要身份**：判据只有一套、看着更整齐，但会破掉正式通道「已经拿到 v1.4.0 就不会被重推同号新正文」的存量保证，用户已明确拒掉。

## Consequences

- 三档各有一份 `latest.json` 与一套版本史（`extension/out/release/oss/`、`extension/out/snapshot/oss/`），快照不会推给正式用户；代价是要「转正」得把同一批代码按正式通道再发一次。两档的**发布身份也不同维**（正式看号、快照看号加摘要），所以 `publish-oss.mjs` 的「同号摘要不同」告警只在正式通道开口。
- 「只启用一个通道」是使用纪律而非硬约束。同页互斥由壳的启动标志兜底：后到的通道不执行远程体，只在控制台留一条指名占用通道的告警。
- 改任何一条 key 等于换一个全新实例（数据从零开始）。三条线一旦定稿就别再动。
- 撤回一个已发布的正文，删 OSS 文件是无效的——正文可能已落进各机器的升级缓存。真正的吊销手段是清单里的 `min` / `shell-min` 门槛与 `blockedId` 隔离；正式通道外加发一个更高版本号，快照通道重发一份新正文（换摘要即换身份）就够了。
- dev 侧一次性代价：`extension/manifest.json` 换成 dev key 后扩展 ID 变了，此前装在旧 ID 上的调试配置在新实例里看不见，需重新配一遍。
