# 异能兽培育 —— 协议台账与设计判据

`src/feats/player/beast-breed/index.js` 的单一真相：号段语义、字段口径、闸门常量、以及每条业务判据的**出处**。
实现只读游戏数据 + 直发 15xx（外加一条 670 聊天分享，见 §2 末），不调游戏的 Update 系列接口改写本地态。

> 证据来源（两类互证，缺任一类都只能算推演）：
>
> - **实录报文**：异能兽培育真人实录三场（2026-10-02 首探 28 条、2026-10-07 主跑 147 条、2026-10-07 申请加油（分享链路）9 条）。
> - **游戏反编译码**：
> `EnigmaBeastController`（枚举与门面）、`RealEnigmaBeastController`（闸门与发包）、
> `EnigmaBeastBreedSelectPop`（出访兽候选口径）、`EnigmaBeastBreedVisitPop(Cell)`（加速/申请入口）、
>   `EnigmaBeastBreedMainPop` / `EnigmaBeastBreedListPop(Cell)` / `EnigmaBeastBreedInfo`（主宠列表与到点判据）、
> `NNewEnigmaBeastBreedShareItem`（联盟分享卡渲染 + 被点方判据）、`ChatShareLinkType`（分享子类型枚举）、
> `EnigmaBeastResCfg`（物种/品质名）、`NRequestIdV2` / `NResponseIdV2`（号段）。

## 1. 玩法闭环

在自家「异能培育基地」挂一只**主宠**（`main`），接受别人申请进来配对；或把自己的兽**寄养**到别人家当 `other`。
双方各出一只 → 等待一段时长（310006 分）→ 到点变 `REWARD` → 由寄养方发 1584 领取新兽。
期间盟友可发 1587「加油」缩短剩余时间。所以脚本要同时管四件事：**出去寄养、别人来寄养、到点领、加速**。

> 术语对照（代码注释用简称，面板文案一律走官方口径，同一个东西不再发明第三套名字）：
> 主宠 = `info.main` = 官方「放置的异能兽」（`enigma_beast020/123/135`）；出访兽 = 我 `apply` 出去寄养的兽；
> 加速/帮助 = 1587，官方叫「加油」（`enigma_beast077/131/132/214`）；在途 = 官方「待同意」（`enigma_beast100`）。

### 本 feat 唯一的非 15xx 出站：670 `PostChatMsg`（分享求加油）

「把我家正在培育的兽分享到联盟频道请盟友加油」不是培育业务包，而是聊天链接（申请加油实录里第 7 条请求 / 第 8 条应答）：走主 socket 的 `cmd=670`，
pack = `{c:2(联盟), m:"link", uid:"", llm:JSON 串, custom:JSON 串, group:""}`，与 `core/chat.js` 的
`send(text, {channel:'alliance', llm})` 完全同构（含 `custom.clientTime = String(fClientTime) + fUid`）。

| `llm` 字段            | 值                                                                | 出处                                                                      |
| --------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `t`                   | `35` = `ChatShareLinkType.ENIGMA_BEAST_BREED`                     | 游戏 `onBreedShareClick` 装箱                                             |
| `pid`                 | 我的 StrUid（自家分享时与发送者同侧）                             | 同上                                                                      |
| `enigmaBeastInfoList` | `[{id,cfgId,star}(我家 main), {id,cfgId,star}(寄养进来的 other)]` | 同上；实录两个 id 与 10132 的 `info.main.id`/`info.other.id` **逐位相同** |
| `uts`                 | `1`                                                               | 同上                                                                      |

`id` 在这里是**十进制字符串**（走 `idStr()`），不是 Int64 实例 —— 与 15xx 的装箱口径不同。
应答 `data` 成功时是 JSON 串 `{"success":1,"m":"link"}`，业务拒时是裸串，故必须 `JSON.parse` 后判 `success===1`。
盟友点这条消息才轮到游戏发 1587（被点方链：功能开 → 培育建筑 → `pid`≠我 → 自己的 310012 未满 → 关系需好友|联盟），
所以**分享不受自己今日加油次数约束**，那套限额是每个加油者自己的。

## 4. 状态枚举与字段语义

### `BeastBreedType`（`EnigmaBeastController`，实证）

`WAIT=0`（空位/等同意） / `BREEDING=1`（培育中） / `REWARD=2`（可领）。用在「培育家信息」的 `breedingStatus` 上。

### 培育家信息（1583 的 `info`、1585 的 `visit[]`、10132 的 `info`、1581 应答的 `info` 同一结构）

```
{ ownerUid:string, breedingStatus:BeastBreedType, breedingEndTimeSec:number,
  main?:兽条目, other?:兽条目, helpUid:string[],
  ownerPlayerInfo:string(JSON), ownerAllianceTag:string,   // 1583 不带后两者时按缺失处理
  lastOfflineTime:number }                                  // 仅 1585：0=在线，否则绝对服务器秒
```

- `main` = 这家的主宠（房主挂的那只）；`other` = 寄养进来的那只（其 `uid` 是寄养方）。
- `helpUid` = 已给这家加过油的 uid 集。它既是 1587 的「没帮过/未饱和」判据，也是**分享求加油的饱和判据**
  （`helpUid.length >= 310011` 就不再往联盟发卡片）。
- ⚠️ 游戏侧的分享按钮闸门是 `main && other && breedingStatus===BREEDING`（`EnigmaBeastBreedMainPop.onBreedShareClick`），
  所以上面那三个条件缺一律不分享；空位（`WAIT`）与可领（`REWARD`）阶段没有可加油的对象，发了只是刷屏。
- ⚠️ `breedingEndTimeSec` 只在 `BREEDING`/`REWARD` 时是绝对秒；`WAIT` 条目里是垃圾值（实录样本恒为 `50400`）。
  脚本只在 `REWARD` 分支读它。
- ⚠️ 1585 条目**不带** `favorite`（该字段在 1571 分享/1589 展示通道里），别照抄 UI 层字段表。

### 我的兽条目（1570 的 `infos[]`、10130 的 `info[]`、1582 的 `apply[]`）

```
{ id:Int64, cfgId, level, star, mainBuff, baseBuff:[…], potential, likeNum, show:bool,
  breeding, levelExp, lock:bool }
```

`breeding`（**我这只兽的占用态**，与上面的 `breedingStatus` 不是一回事）：
`0=空闲` / `1=已派在别人家` / `2=当我家主宠`。

实录核对（按 Int64 的 `_high*2^32 + _low` 精确对值，不用 JS number）：

- `2=主宠`：两份实录的 1570 池里各**只有一只** `breeding=2`，id 均为 `4629875604343294467`，
  与同一份 10132 推送的 `info.main.id` **逐位相同**；863 只分布 `{0:862,2:1}`、610 只 `{0:609,2:1}`。
- `1=已派出`：发完 1580 后紧跟的 10130 推送把那只被申请的兽标成 `breeding=1`（两份实录各一例）；
  而 1570 读发生在 1580 之前，故样本里 `breeding=1` 计数为 0 —— 时序自洽，不是反例。

⚠️ **Int64 精度铁证**：同一个 id 若走 `JSON.parse` 的 JS number，会得 `4629875604343295000`（偏差 533）。
所以读必须 `String(int64Instance)`（游戏 Int64 自带精确 `toString`）、发必须 `bits.int64(十进制串)`；
直传 number 会拿到一个服务器不认识的 id。

### 1583 的语义边界（实录纠正了本条最初的设想）

1583 只列**我的兽在别人家**（含等待同意的 `apply` 条目）；**我家自己那条不在里面**，只在 10132/1581 应答的
`info` 里。所以：

- 「在途申请集合」= 1583 中 `apply` 非空的条目，`info.ownerUid` 是目标家、`apply.id` 是我的兽；
- 「我家待领」只能来自 10132 缓存，「别人家待领」来自 1583。
- ⚠️ `apply.uid` 实测等于 `info.ownerUid`（目标家），**不是**我 —— 判在途一律用 `info.ownerUid`。
- 1581 的 `id` 是**对方**的兽：实录里 `1581.id = 4840988610324979712` 等于 1582 `apply[0].id`、
  也等于随后 10132 的 `info.other.id`（其 `uid` 是申请人），且**不在**我的 1570 池内 —— 三条互证。

## 7. 脚本侧决策与取舍

- **轮首玩法开启闸**（`gameData.beastBreedOpen`，ACL 收口，镜像游戏 `isOpenFunc(BeastOpenType.BREED, false)`：
  `FunctionOn(enigma_beast_breeding) && openState ≥ BeastServerStatus.BREED`）：培育未开放/未开始时服务器对 15xx
  干脆不回包（实测每条白等 15s 超时后报 `no server response`，四条读通道连刷读失败 warn）——闸关直接按 IDLE 档
  睡过去不发任何包，控制器 openState 被 21876 推送翻转后自然放行。符号缺失（subpack 未接管）同样回 false（fail-closed）。
  旧实录佐证：活动未开始窗口内 cmd 1582/1583/1585 均超时，无任何应答帧。

- **目标两种互斥模式**：`specify`（只在 `cfg.uids` 名单内挑，名单是用户显式意志，故不再套联盟/离线阈值，
  但仍守 `WAIT`、不在途、未拉黑）/ `random`（1585 全量按五级过滤链取候选后等概率随机一个）。
  服务器侧还有一条硬约束落在文案 `enigma_beast239`「对方不是您的好友或联盟成员」—— 1585 本身就是可拜访集，
  天然满足，故脚本不再重复判好友关系。
- **随机口径逐级回退**：过滤后为空时先放宽离线阈值、再放宽联盟闸门，仍空才本轮跳过并 `log.warn`。
  窄口径导致「整轮空转且无声」是这类 feat 最难查的故障，故回退与告警都是必需的。
- **配额 fail-open**：`breedData` 缺失（还没收到过 10132）时不硬拦每日次数，靠服务器拒绝回落。
  与联盟科技的 honor 闸门同风格 —— 宁可多发一次被拒，也不因缓存缺失整轮停摆。
- **拒绝分类与当日收敛**：PBV2 拒绝原因的多语言 key 落在 `header.d`（`core/net.js` `sendPBV2` 已归一到 `Ret#reason`，`rejectText` 优先读它）——
  早先 `sendPBV2` 丢弃 `header` 致 `rejectText` 只看到空 `data`，「次数耗尽」判据沦为死代码。现按服务器真实 key 分类（1116 录制实证）：
  1580 命中 `enigma_beast130`（今日培育次数已达上限）置 `exhausted`，当日不再申请；1587 命中 `enigma_beast132`（今日加油次数已达上限）置 `helpExhausted`，当日不再加油；
  两标记在 10132 显示额度回升（如买次数）时提前解除，否则跳日清；领奖照常跑。旧判据键 `enigma_peiyu_times_8` 是客户端本地预检文案，服务器从不回它，已废弃。
  不做按 uid 拉黑：瞬时/异常拒绝不该把指定玩家整天封掉，下一拍重读 1585/1582 自然收敛。
- **10132 缓存口径**：net 观测面已剥 pbAckV2 信封，`ev.data` 即 breedData 业务体本身；raw 池化复用，跨拍持有须快照字段
  （`snapshotBreedData` 只取四个标量配额 + info 最小字段集，兽 id 顺手箱成十进制串）。旧版多读一层 `ev.data.data` 恒为 undefined，
  配额缓存从未被推送刷新、闸门全部 fail-open，是「培育已达上限」刷屏的根因。
- **超时撤单**：1583 的 `apply` 条目不带发起时间戳，故本地按 `inflightSeen[uid]` 判 TTL，超期发
  `1580 apply:false` 撤回，腾出 310008 名额。阈值不进面板，固定为常量 `APPLY_TTL_HOURS = 6`（覆盖
  「对方当天上线一次就够」）。账本落 `storage.data['beastBreed.ledger']`（UID 隔离，字段
  `{day, exhausted, helpExhausted, seen, shareAt}`），跨 reload 保留首发时刻 —— 否则刷新一次页面就把 TTL 重新起算，
  超时单永远撤不掉。
- **全量读失败 ≠ 空集**：`readAll` 把读失败与读到空分开（前者返回 `null`）。把读失败当空集会算错在途数，
  进而超发申请；也会把 `firstSeenAt` 整表误删。宁可不发也不猜。
- **择时四档**：`cycle.pending → 0`；有待领未到点 → `min(到点-now, ACTIVE)`（绝对点仍属 A）；
  有在途/在培育 → `ACTIVE`（5 分）；全空闲/配额用尽/无候选 → `IDLE`（30 分，也是 cycle 的 fallback）。
- **不主动换主宠**：已有 `breeding===2` 或 `info.main` 就一律不动 1579 —— 换主宠会打断进行中的配对。
- **1586 不调**：`CANCEL` 会中断本次培育且**不返还次数**（文案 `enigma_beast248`），脚本只在
  「等同意」阶段用 1580 `apply:false` 撤单，绝不在培育中回收。
- **面板按模式收起**（`fd.showIf`，ui.js 的通用能力）：两模式互斥，故「指定玩家」下只留名单 + `agreeList`，
  「随机玩家」下只留 `allyOnly` / `maxOfflineHours` / `autoAgree`，另一侧整片 `hidden`（连该段没剩字段时
  小标题一起收起）。两侧各一个控件、由 `toModuleCfg` 折成单一档位 `cfg.autoAgree ∈ off/ally/all/list`
  —— 下游一律只读 `autoAgree`，不再判 `mode`。`list` = 只处理名单内申请人的申请。
  显隐只切 `hidden` 不重建 DOM（`ui.refresh` 本就不重刷结构，重建会丢掉已绑控件事件）；配套两条 CSS
  `[data-dep][hidden]` / `.pc-fsec[data-sec][hidden]` 是必需的 —— 作者类规则给了 `display`，UA 的
  `[hidden]{display:none}` 会失效，故用双属性选择器把特异度抬到 0,2,0。
  取舍：没让 `autoAgree` 的 option 列表随模式变（函数 options 在不重建 DOM 时刷新不了 `<select>` 选项）。
- **面板只留用户能判断的东西**：`applyIntervalMs`（发包限流）与 `helpPerTick`（单轮加油数）不下放给面板，
  落成模块常量 `APPLY_INTERVAL_MS` / `HELP_PER_TICK` 并由 `toModuleCfg` 恒输出（defaults 也不再带这两个 key，
  故旧存档的值不再生效）—— 调小只会撞服务器频控、调大只是拖慢一轮，用户没有判断依据。
  同一口径往后推平：在途名额 `maxInflight` 恒跟随游戏上限 310008（调小只会少培育，调大服务器硬拦）、
  超时阈值即上述 `APPLY_TTL_HOURS`；两者一度被收进默认折叠的「高级（名额与超时）」子分组，最终整段撤下面板，
  只留常量与 `toModuleCfg` 里的默认输出。
  同时撤下「状态」段与它背后的整条只读数据链（`view` / `updateView` / `formatTodayState` / `formatMainState`
  及配套的 `bus.emit('ui.refresh')`）—— 只读展示不改变任何行为，占面板却不供决策，干脆全部拆除。
  面板最终分段：培育对象 | 派出的兽 | 我放置的兽 | 自动领奖与加油（无折叠段）。
- **属性维度一行一个设置项**（用户口径：[属相][品种][品质] 同一行）：三个面板块（培育对象下的「匹配的兽」/
  「派出的兽」/「我放置的兽」）统一采用新增的 `type:'tripick'` 字段——一个 label 接三个 `select`（同一行横排，
  紧凑 72px 宽），每个 part 自己一个 `data-key`，change/syncControls 仍走 `select.pc-fsel` 的同一条陆径（不需在 wire/panel
  侧特例接线）。首项固定「不限」（值 0），`normOne = normNums` 依旧将 0/空串/旧档 `[]` 归为空数组，
  下游一律以「空数组 = 该轴不参与筛选」同一口径。
- **随机模式「按属性找培育对象」**（`reqFactions/reqTypes/reqQualities`，`showIf: isRandom`）：属性匹配不再带开关
  （`reqMainBeast` 已从面板/cfg/defaults/toModuleCfg 移除）：三个下拉任一非「不限」即启用匹配；三项都取「不限」
  面板行仍在，但不参与过滤。启用后，在原有「WAIT → 不在途 → 联盟 → 离线」的过滤链上多一道④：取 1585
  条目的 `main.cfgId` 查 enigma_beast 行，三个维度均命中才当候选。没挂主宠的家一律出局（启用本身就在说「要对方有
  符合的兽」）；行取不到同样出局（fail-closed，与同 feat 「全量读失败 ≠ 空集」一个族）。三级回退链（离线 → 联盟）
  仍保留但不自动放宽属性，因为属性是用户显式意志。
- **分享求加油只在有对象且未满时开口**（`shareForHelp`，段④尾部）：自家 `BREEDING` 且 `main`&`other` 俱在
  才发 670；`helpUid.length >= 310011`（已被加满）或本轮未到间隔则闭嘴。间隔是唯一放上面板的节奏参数
  `shareIntervalMin`（默认 30 分 / 下限 5 分，再小就是刷联盟频道）—— 它是用户能判断的（“多久催一次”）。
  发出去的时刻落账本 `shareAt`，而非内存变量：否则刷新一次页面就把间隔重新起算，联盟频道会被同一只兽刷屏。
  被拒（含 `pocketcc.chat` 不在场）不记时刻，下轮可重试；自家不在培育 / 非自己名下的 `info` 一律不动。
